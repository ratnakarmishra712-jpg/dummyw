Viva preparation guide · architecture · tools · security application

Defend the project in a viva

The one paragraph to internalise

ReconToReport is a pipeline orchestrator that runs a sequence of open-source and custom security tools in attacker order — recon → authenticated access → scanning → exploitation → harvest → report — and forces every tool's output into one shared database. The intellectual contribution is that integration: because findings live in one store, a later tool can act on what an earlier tool discovered, turning isolated scans into a demonstrated attack chain. Everything else — the grade, the ATT&CK mapping, the report — is a view over that store. If you understand why the shared store matters, you can answer almost anything.

Broad architecture — four layers + one store

Input
CLI or web UI — you give a target URL and pick phases; active phases need an explicit authorization flag.
↓
Config
One Config object — target, scope rules, auth roles, tool paths, stealth options — built from a form/flags.
↓
Orchestration
Orchestrator — resolves phase dependencies, enforces the authorization gate, runs each phase in isolation so one failure never kills the run (per-phase try/except + timeouts).
↓
Execution
5 phases shelling out to tools and running custom checks — each reads/writes the shared store.
↓
Storage
SQLite via an ORM — one schema (targets, assets, transactions, auth-contexts, findings, secrets, reports) every phase shares. This is the heart.
↓
Output
Report generator + UI views — severity-ranked report, A–F grade, attacker story, ATT&CK kill chain, Navigator export.

How a run actually works

Phase 1 Recon — passive subdomain discovery, a built-in crawler that maps pages/forms/params and saves response bodies, and content/directory fuzzing for hidden files. Phase 2 Access — logs in as configured roles (real browser or a pasted cookie) and stores each session with a privilege level; can passively capture traffic. Phase 3 Scan — a template engine for known flaws, a security-header/CORS audit, the broken-access-control differential, and a behavioural XSS check. Phase 4 Exploit — token (JWT) analysis, error-based SQL injection, open-redirect and path-traversal probes, and sqlmap when present. Phase 5 Harvest — scrapes exposed secrets from captured traffic, then renders the report. Each phase reads what the previous wrote; the order mirrors a real engagement.

Q&A — architecture & design

Isn't this just a wrapper around existing tools?

Deliberately, yes — the contribution isn't a new exploit, it's the integration. A shared data store lets a later tool use what an earlier one found, so you get a demonstrated chain instead of five disconnected tool outputs. A bag of scripts can't do that.

Why a shared database instead of passing data between tools directly?

Tools emit wildly different formats. Normalising everything into one schema means any phase can query any earlier result uniformly, the report has a single source of truth, and adding a new tool means writing to the same tables — no rewiring. It's the integration layer.

Why phases, and why that order?

The order mirrors a real engagement: you can't test authenticated access before you've logged in, can't exploit a parameter before recon found it. Phases make dependencies explicit and let the orchestrator run them with isolation and retries.

What happens if one tool crashes or hangs?

Each phase runs inside try/except and each external tool call has a timeout; a failure is logged and recorded as a phase result, then the run continues. One tool dying never takes the whole run down.

How do you keep false positives down?

Findings carry a confidence level; XSS is only rated high if it actually executed in a real browser; the access-control finding only fires on a genuine success the low-priv user shouldn't get; and harvested secrets are quarantined in a separate table until a human promotes them.

How is scanning kept within authorization?

Scope rules (host allow/deny) gate every active request, and phases that send traffic refuse to run without an explicit "I have authorization" flag. Passive, offline steps (like secret scraping) run without it.

Q&A — tools & how they work

Walk me through the broken-access-control check.

For each protected page it makes three requests — anonymous, as a high-priv session, as a low-priv session — and compares. A finding fires only when anonymous is denied, the privileged user is allowed, and the low-priv user is also allowed: the page is gated, but the wrong person gets in. It needs two identities held at once, which is why a stateless scanner can't produce it.

How does the SQL-injection check work without external tools?

It appends a single quote to each parameter and re-requests; if a recognisable database error surfaces in the response, the input is reaching a query unsanitised. sqlmap is used too when installed, but the built-in check means SQLi detection has zero dependencies.

How does the XSS check avoid guessing?

It injects a unique marker into a parameter, loads the page in a real headless browser, and checks whether the marker reaches the DOM unescaped or actually triggers script execution — rated high only if it fired.

Where do the CWE and ATT&CK numbers come from?

CWEs are assigned by our custom checks and by the template engine's metadata. For ATT&CK, the technique names and official URLs are loaded from data distilled directly from MITRE's ATT&CK STIX bundle; which technique a vulnerability class maps to is our own curated ruleset, because MITRE publishes no canonical CWE-to-technique mapping. It's a deterministic, auditable lookup.

How do the open-redirect and path-traversal checks confirm a hit?

Open redirect: inject an external URL into redirect-style params and see if the server sends the browser off-site (without following it ourselves). Traversal: inject a ../../etc/passwd payload and confirm by the unmistakable root:x:0:0 signature in the response.

Q&A — security application of R2R

Who uses this and for what?

Authorized security testers and internal red/purple teams, to turn one URL into a prioritized, evidence-backed picture of an app's risk in minutes — automating the reconnaissance-to-access-to-escalation workflow that's otherwise slow and manual, and producing the client deliverable automatically.

How is this different from a vulnerability scanner?

A scanner answers "what's broken?" and hands you a list. R2R answers "what could an attacker chain together?" — it operates as an authenticated identity and proves escalation end-to-end, which a stateless scanner architecturally cannot. We still run the scanner-style sweep too, so we're never behind on coverage.

If it's an attacker tool, how do you have the credentials in the first place?trap

We don't need privileged creds. The finding is that a normal account — the kind anyone self-registers, phishes or buys in thirty seconds — reaches things it shouldn't. A low-priv foothold is the cheap, everyday start of a real attack. Any admin session we hold is just a reference to confirm "this page is genuinely protected," to avoid false positives — not part of the attack.

Is the ATT&CK mapping real or made up?trap

The technique IDs, names and URLs are genuine MITRE identifiers, loaded from their official STIX bundle and version-pinned — we can refresh them with one script. The only thing we author is the mapping from our finding types to those techniques, because no canonical source for that exists.

Could this be misused offensively?

It only does pre-exploitation testing, every active phase is gated behind an explicit authorization flag and scope rules, and it stops short of destructive actions. It's the same dual-use posture as every pentest tool — built and gated for authorized testing.

What are its limits? (say these proactively)

It's pre-exploitation adversary emulation for web apps — no command-and-control, no lateral movement, no evasion. It finds known/common weakness patterns, not business-logic flaws, and some findings still want manual confirmation. Being upfront about scope is a credibility signal, not a weakness.

The 5-point cram: (1) it's an orchestrator, not a new exploit; (2) the shared store is the novelty — tools chain off each other; (3) flow = recon → access → scan → exploit → harvest → report; (4) flagship = broken access control a normal account shouldn't have, impossible for a stateless scanner; (5) honest scope = pre-exploitation web emulation, some findings need manual confirmation.
