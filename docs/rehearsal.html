Part 1 · The talk (~3 min)

Hook ~30s · hands off keyboard

"Most security tools run a vulnerability scan — they fingerprint a target and hand you a checklist of weaknesses. But a list of weaknesses isn't an attack. A red team does something different: it emulates a real threat actor — reconnaissance, a foothold, escalation, impact — and proves how far an adversary could actually get. ReconToReport automates that red-team workflow. One web address in; it runs the adversary's kill chain in order and produces the operator's report at the end. Let me walk the kill chain — the sequence is the whole point."

Beat 1 — Footprint the target Recon

"It opens the way an operator opens an engagement — reconnaissance. It passively enumerates the org's other hosts from open-source intelligence, never touching their infrastructure, then maps the live attack surface: every page, form and input, plus forgotten assets — backups, exposed source, unlinked admin panels. By the end it holds the target map an adversary builds before making a move."

Beat 2 — Establish a foothold Access

"Here it stops being a scanner. A scanner tests logged-out, as an anonymous stranger. Real operators work from inside, as a valid account — and a low-privilege account is the cheapest foothold there is: you register one, or phish, or reuse a leaked session. The tool authenticates and holds that session, tagged with its privilege level. That shift from outsider to authenticated operator unlocks every technique after it."

Beat 3 — Find the way in, then escalate Scan

"With the map and a foothold it goes hunting. Part of this is the known-vulnerability sweep a scanner does — so we're never behind on coverage. But then it runs a technique a scanner structurally cannot: privilege escalation. Holding two identities at once, it asks whether a low-privilege account can reach what should be staff-only — and when a throwaway user walks into an admin function, that's broken access control, proven. It also confirms code execution by firing payloads in a live browser, and audits the defensive posture the blue team relies on."

Beat 4 — Weaponize & prove impact Exploit

"An operator demonstrates impact, not just 'this looks weak.' It tests whether session tokens can be forged — forge one and you impersonate any user. It drives injection into the database, the path most real breaches run through. It reads files off the server, and checks whether the trusted domain can be weaponized as a phishing redirect against its own users. Every hit is logged as repeatable proof."

Beat 5 — Collect the loot, write the report Harvest + Report

"Then collection — the credentials, API keys and tokens an adversary would exfiltrate, pulled from the captured traffic. And the operator deliverable: findings ranked by severity with impact and fixes, a single A-to-F grade, a first-person 'this is how I compromised you' narrative, and every finding mapped to its MITRE ATT&CK technique on the kill chain — exported as a layer the client opens in the official ATT&CK Navigator. The whole engagement, from one web address."

Close — the one point that wins ~20s

"What separates this from pointing five tools at a target: every phase writes into one shared store, so each technique builds on the last — the foothold feeds the escalation, the map feeds the exploitation, the captured traffic feeds the collection. A scanner runs checks in isolation and hands you disconnected findings. We run the adversary's TTPs in kill-chain order, each feeding the next — so you don't get 'five weaknesses,' you get the chained path a threat actor takes to compromise. That chaining is the thing a bag of tools can't reproduce."
Part 2 · Live demo (~2 min)

Choreography narrate each beat as it runs

  1. Set up. "Both tools against the identical target — here's the demo app." Start the bundled target, point R2R at it, hit run.
  2. Narrate the kill chain as phases fire — use the Beat lines above: "mapping the surface… now operating as two identities… now comparing what each can reach…" The live log paces you.
  3. Land the knockout. Stop on the broken-access-control finding: "anonymous is denied, but the normal user reached the admin page — privilege escalation, proven, with a two-line repro."
  4. Show the output. Open the ATT&CK page (kill-chain coverage + next moves + Navigator export) and the report with its A–F grade and attacker-story.
  5. The line: "Run your scanner on this same box — it won't produce that escalation finding, because it has no concept of who it's logged in as. We hold both identities and compare."
If the demo breaks: the header-audit, built-in SQLi and the access-control check run on the local target with nothing installed — that's why they exist. Worst case, narrate over the pre-generated report you opened in a spare tab. A phase erroring live is a feature: "notice it kept going — one tool failing never kills the run."
Part 3 · Mock viva — drill these out loud

Architecture & design

Isn't this just a wrapper around existing tools?

Deliberately — the contribution is the integration. One shared store lets a later tool act on what an earlier one found, so you get a demonstrated chain, not five disconnected outputs. A bag of scripts can't do that.

Why a shared database instead of piping tools together?

Tools emit different formats; normalising into one schema means any phase can query any earlier result, the report has one source of truth, and a new tool just writes to the same tables. It's the integration layer.

What if a tool hangs or crashes mid-run?

Each phase runs in try/except, each external call has a timeout; a failure is logged and recorded as a phase result, then the run continues. One tool dying never kills the run.

How do you keep false positives down?

Confidence levels per finding; XSS only high if it actually executed; the access-control finding only fires on a genuine success the low-priv user shouldn't get; harvested secrets are quarantined until a human promotes them.

Tools — how they actually work

Walk me through the privilege-escalation check.

Three requests per protected page — anonymous, high-priv, low-priv — compared. It only fires when anonymous is denied, the privileged user is allowed, and the low-priv user is also allowed: gated, but the wrong person gets in. It needs two identities held at once, which is why a stateless scanner can't do it.

How does the XSS check confirm, not guess?

We inject a unique canary plus a small HTML tag into a parameter and render the page in a real headless browser. If the tag comes back unescaped in the DOM, the app isn't encoding output — medium. If a JavaScript dialog actually fires, our code executed — high. The real browser is what proves execution.

Explain the open-redirect check — and how does that help an attacker?

We put an external address in redirect-style params and, without following the redirect, check whether the server's 'go here next' points off-site. It helps an attacker because they craft a link on the trusted domain — bank.com/login?next=evil.com — and phish it to a victim; the victim trusts the real domain, clicks, and the site itself forwards them to the attacker's page. The redirect launders the attacker's destination through a domain people and mail filters trust. Our tool only detects the flaw; delivery is the attacker's own phishing.

Explain the path-traversal check.

Where a parameter names a file, an attacker climbs out of the intended folder with ../ sequences — ../../../../etc/passwd. We inject that and confirm the hit by the unmistakable root:x:0:0 signature of that system file in the response. A hit means arbitrary file read — configs, source, secrets.

Where do the CWE and ATT&CK numbers come from?

CWEs are assigned by our checks and the template engine's metadata. For ATT&CK, the technique names and official URLs come from data distilled from MITRE's STIX bundle; which technique a CWE maps to is our curated table of ~40 web weakness families — MITRE publishes no canonical CWE-to-technique map, so it's a deliberate, auditable lookup.

Security application of R2R

How is this different from a vulnerability scanner?

A scanner answers 'what's broken?' and hands you a list. R2R answers 'what could an attacker chain together?' — it operates as an authenticated identity and proves escalation end-to-end, which a stateless scanner architecturally cannot. We still run the scanner-style sweep, so we're never behind on coverage.

If it's an attacker tool, how do you have credentials in the first place?trap

We don't need privileged creds. The finding is that a normal account — the kind anyone self-registers, phishes or buys in seconds — reaches what it shouldn't. A low-priv foothold is the cheap, everyday start of a real attack. Any admin session we hold is just a reference to confirm 'this page is genuinely protected,' to kill false positives — not part of the attack.

Is the ATT&CK mapping real or made up?trap

The IDs, names and URLs are genuine MITRE identifiers from their official STIX bundle, version-pinned, refreshable with one script. The only thing we author is which technique our finding types map to, because no canonical source for that exists.

Could this be misused offensively?

It only does pre-exploitation testing, every active phase is gated behind an explicit authorization flag and scope rules, and it stops short of destructive actions — the same dual-use posture as every pentest tool.

What are its limits? (say these before you're asked)

Pre-exploitation adversary emulation for web apps — no command-and-control, no lateral movement off-host, no evasion. It finds known patterns, not business-logic flaws, and the XSS check covers reflected/ DOM sinks on GET parameters, not stored XSS. Some findings still want manual confirmation. Owning the scope is a credibility signal.

Part 4 · If you blank
The 5 anchors: (1) it's an orchestrator, not a new exploit; (2) the shared store is the novelty — tools chain off each other; (3) flow = recon → foothold → escalate → exploit → collect → report; (4) flagship = a normal account reaching admin-only, impossible for a stateless scanner; (5) honest scope = pre-exploitation web emulation, some findings need manual confirmation.

Universal fallback when cornered on a detail: answer at the mechanism level — "it sends this and looks for that signature" — which is always true and never trips you up.
